# ATM Cash Dispenser API (日本語版)

[🌐 English Version](./README.md)

## 🎯 本プロジェクトが解決する課題

本プロジェクトは、ATMの現金払い出し処理を以下のような現実的な制約のもとでシミュレーションするWeb APIです。

- **限られた現金在庫**の厳密な管理
- **複数リクエストの同時実行**（マルチスレッド環境での並行処理）
- 途中失敗を許さない**アトミックなトランザクション要件**（All-or-Nothing）

特に、金融システムや決済系システムにおいて最重要課題である、**「並行アクセス下における状態変化の整合性と正確性の担保」**に焦点を当てて実装しています。

---

## 👤 開発の意図と取り組み

本プロジェクトは、単に「動くコード」を作るだけでなく、以下のソフトウェアエンジニアリングの実践を証明するために設計・実装しました。

- **堅牢なドメインモデリング**：不変条件（不正な状態）を型レベルで防御する設計
- **スレッドセーフな状態管理**：マルチスレッド環境における共有リソースの安全な制御
- **責務の明確な分離**：ドメイン駆動設計（DDD）の思想を取り入れた3層レイヤードアーキテクチャ

すべての設計判断（`lock` の使用、Singletonの採用、値オブジェクトの導入など）は意図を持って選択されています。詳細は後述の「主要な設計判断」を参照してください。

## 🏗 アーキテクチャ

本プロジェクトは以下の3層構造を採用し、コアとなるビジネスロジック（Domain）がフレームワークや外部入力に一切依存しない構造を徹底しています。

```text
src/
├── AtmCashDispenser.Domain/       # ドメイン層（純粋なビジネスロジック）
│   ├── Dispensing/                # 在庫管理（CashInventory）・払い出し計算（Calculator）
│   └── Shared/                    # Money, Denomination（値オブジェクト）
├── AtmCashDispenser.Application/  # アプリケーション層（ユースケースの制御）
│   └── DispenseCash/              # UseCase・各種DTO
└── AtmCashDispenser.Api/          # API層（HTTPエンドポイント・Minimal API）

```

* **Domain**: 純粋な業務ロジック。外部フレームワークへの依存ゼロ。
* **Application**: ユースケースの流れを調整（ドメイン呼び出しとDTOへのマッピング）。
* **API**: HTTPリクエストの受付と、JSONのシリアライズ・デシリアライズを担当。

## 🚀 主要な設計判断（トレードオフの言語化）

### 1. `lock` 文によるアトミックなトランザクション制御

ATMの払い出しでは、すべての金種の在庫が確定するまで、一部の金種だけを減算するような「中途半端な状態」を絶対に発生させてはなりません（All-or-Nothing）。

* **判断**: 在庫のチェックから減算にいたる一連の処理全体を `lock` 文でクリティカルセクション化しました。
* **理由**: `ConcurrentDictionary` はキー単体の読み書きはスレッドセーフですが、今回のように「複数キーにまたがる一括操作」の整合性は担保できません。そのため、操作全体を同期化する `lock` が最適であると判断しました。

### 2. インメモリ在庫における `Singleton` ライフサイクルの採用

* **判断**: `CashInventory` のインスタンスをDIコンテナに `Singleton`（単一インスタンス）として登録しています。
* **理由**: 実際のATMハードウェア内に現金が物理的に格納されている状態をシミュレートし、すべてのHTTPリクエスト間で共通の在庫状態を正しく共有・同期させるためです。実務でRDBを導入する場合は `Scoped` に移行し、行ロック等で担保します。

### 3. 値オブジェクト（Value Object）による不変条件の強制

* **Money**: 金額がマイナスになることを初期化時に防ぎます。
* **Denomination**: 日本円に実在する有効な金種（10000, 5000, 1000など）のみを許可し、不正な金種の流通を型レベルで不可能です。
* **効果**: 不正な状態を「そもそも作れない」設計にすることで、システム全体の堅牢性を高めています。

### 4. 例外ベースのドメインバリデーション

* **判断**: 在庫不足や、手持ちの金種ではお釣りが計算できないケースの制御フローに、ドメイン固有の例外（`CannotDispenseException` 等）を採用しています。
* **今後の展望**: C#の標準的な記述に準拠していますが、高頻度で発生するビジネスエラーに対して例外をスローするのはパフォーマンス（スタックトレース生成コスト）の観点で改善の余地があります。次のステップでは、型安全に成否を返す `Result<T>` パターンへのリファクタリングを予定しています。

## 🧪 テスト戦略

自動テストによる「変更に対する安心感」を重視し、xUnitを用いた3つのテストレイヤーを構築しています。

* **✔ ドメイン単体テスト (カバレッジ100%)**: 払い出しアルゴリズムの数学的正確性、境界値、不変条件のガードを網羅。
* **✔ アプリケーション統合テスト**: ユースケースのフローを検証。入力値がドメインモデルに正しく変換され、在庫状態が変化することを確認。
* **✔ APIインテグレーションテスト**: `WebApplicationFactory` を使用。インメモリのテストサーバーを起動し、ルーティング、HTTPステータスコード（200 OK / 400 BadRequest）、JSONの構造（契約）をエンドツーエンドで検証。

---

## 💪 本システムが保証すること

1. 複数のリクエストが同時に来ても、在庫データの競合（レースコンディション）が発生しない。
2. 払い出し計算に失敗した場合、在庫が中途半端に減るようなデータの不整合が起きない。
3. 不正な金額や存在しない金種がドメイン層に侵入しない。

## 📡 API 仕様

### `POST /dispense`

指定された金額の払い出しを計算・実行します。

**リクエストボディ**

```json
{
  "amount": 16000
}

```

**レスポンス (200 OK)**

```json
{
  "items": [
    {
      "denomination": 10000,
      "count": 1
    },
    {
      "denomination": 5000,
      "count": 1
    },
    {
      "denomination": 1000,
      "count": 1
    }
  ]
}

```

**エラーケース (400 Bad Request)**
以下の条件時、適切なエラーコンテキストと共に400エラーを返します。

* 金額が不正（0以下、またはバリデーションエラー）
* 対応できない金額（金種で割り切れない）
* ATM内の在庫不足

## 🔮 今後の改善展望（ロードマップ）

製品版（Production-Ready）へのステップとして、以下の拡張を想定した設計にしています。

1. **永続化層の導入**: EF Core + SQLite を導入し、リポジトリパターンを用いてDBレベルでのトランザクション・行ロックへ移行。
2. **Resultパターンの適用**: ドメイン例外を `Result<T>` コンテナに置き換え、制御フローの予測可能性とパフォーマンスを向上。
3. **グローバルエラーハンドリング**: ASP.NET Core ミドルウェアを構築し、システム例外をキャッチして Web標準の **RFC 7807 (Problem Details)** 形式のJSONを自動返却。
4. **構造化ロギング**: Serilog等の導入によるオブザーバビリティの確保。
